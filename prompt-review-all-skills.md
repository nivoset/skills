## Recommended rule set

1. When multiple skills match, apply the most specific active skill, then repository policy, then global policy; record the precedence used.
2. Treat a rule as active only when it directs an actor or constrains a workflow; label examples, quotations, and headings explicitly.
3. For every write gate, bind authorization to an exact target/action/payload, actor, timestamp, and retry scope; absent that evidence, remain read-only.
4. For every `blocked` result, record owner, missing input, recovery action, retry/timeout condition, and evidence required to resume; silence is never approval.
5. For every readiness/pass/completion claim, record the checklist, exact evidence artifacts, commit or source state, and owning verdict authority.
6. Allow narrow, explicitly recorded exceptions for required fixtures/configuration/report artifacts while preserving source-code and external-write boundaries.
7. If a rule is intentionally invariant for safety, privacy, security, or data loss, keep it absolute and document why; otherwise use an observable if-then condition with fallback.
8. For composite review lanes, define one responsibility question plus a bounded checklist, or split the lane; do not mix unrelated verdicts.
9. For tracker/browser/test evidence, record stable identifiers, timestamps, environment details, command results, and provenance sufficient for independent re-verification.
10. When a companion skill has a narrower lifecycle or authority model, state explicitly that it overrides generic defaults within its scope.
